`withAdvisoryLock<T>(prisma, key, fn, logger?): Promise<T | null>` is defined at `advisory-lock.ts:58`. Its contention semantics, exactly:

- Acquisition uses **`pg_try_advisory_lock`**, not the blocking `pg_advisory_lock` — `advisory-lock.ts:64`.
- A losing instance returns `null` immediately: `if (!rows?.[0]?.locked) return null;` — `advisory-lock.ts:68`. One round-trip, no queueing, no blocking.

- Release is in a `finally` (`:72`), so a throwing `fn` still unlocks and the error propagates to the caller's `try/catch`.

### 1.4 Two honest gaps

> ⚠️ **Four jobs carry no advisory lock**: `NotificationsCron.scanTasksDue` (`notifications.cron.ts:16`), `NotificationsCron.scanApprovalsPending` (`notifications.cron.ts:61`), `NotificationsCleanupCron.cleanupOldNotifications` (`notifications.cleanup.cron.ts:14`) and `KitchenExpiryCron.handleExpiredPrepBatches` (`kitchen-expiry.cron.ts:12`). These are the four pre-P6 jobs; the eight locked ones all carry the P6-era doc comment about N instances. The cleanup job is harmless (a second instance deletes zero rows) and the two QStash scans are backstopped downstream by `NotificationDispatcher`'s per-`(user, type, reference_id)` cooldown (`notification-dispatcher.service.ts:70`). **`KitchenExpiryCron` is the one with a real exposure**: on N instances, N concurrent runs can each read the same expired batches and each insert a `WasteLog` row, double-counting `cost_impact`. There is no conditional guard on the `createMany`.

> ⚠️ **Four decorators pass no `timeZone` option** — `notifications.cron.ts:16`, `notifications.cron.ts:61`, `kitchen-expiry.cron.ts:12` and `event-holds.cron.ts:60` (the last immaterial, being a 5-minute interval). Those three hourly jobs therefore fire on **process-local** time. `backend/src/main.ts:1` states that "the process timezone is deliberately NOT forced here … the server's own zone is irrelevant" — true for business-day arithmetic, all of which routes through `nodeDayKey(timeZone, …)`, but **not true for cron firing times**. On a UTC container, `'0 * * * *'` fires at :30 IST, not :00 IST. `TZ` is not present in `backend/.env.example` and is not validated anywhere in `backend/src/config/env.validation.ts`, so a fresh deployment fails open silently. The one-line remediation is to add `{ timeZone: DEFAULT_NODE_TIMEZONE }` to the four un-zoned decorators, matching the other eight.

### 2.2 EventEmitter2 and the after-commit discipline

`EventEmitterModule.forRoot()` is registered with **no options** — `backend/src/app.module.ts:99` (`@nestjs/event-emitter` `^3.0.1`, `backend/package.json:41`). Defaults therefore apply: `wildcard: false`, module global. Because wildcards are off, `@OnEvent('order.*')` would not fire — every subscription is a literal string match, which `mission-bridge.listener.ts:11–13` records as deliberate: one explicit decorator per event so the subscribed set is greppable.

**There is no outbox table, no `AsyncLocalStorage`, and no generic deferral primitive.** The after-commit rule (SPEC §4.1) is **positional and by convention**: every emit statement sits lexically *after* the `await this.prisma.$transaction(...)` expression resolves. Verified at every site — for example `orders.service.ts:208` closes the transaction and `:212` emits; `kds.service.ts:232` closes and `:239` emits; `fulfilment.service.ts:752` closes and `:758` emits; `tasks.service.ts:526` closes and `:531` emits.

`emitDomainEvent(emitter, name, payload)` (`domain-events.ts:302–312`) is **not** a deferral primitive — it is a failure-isolation wrapper, `try { emitter.emit(...) } catch { logger.warn(...) }`. It knows nothing about transactions.

Where data has to escape the transaction to reach the emit, a **hand-rolled per-call seed object** is used. Three instances:

- `CascadeOutbox` — the only place using the word. Interface at `approvals.service.ts:63–72`, allocated at `:315` and `:430`, mutated inside the transaction by `cascade()` (`:603`), drained after commit by `emitAfterCommit(outbox, actorId)` (`:618–632`). A plain object holding two nullable seeds, not a queue — not shared, not global, discarded on return.
- `ValidateTaskResult.event` — seeded inside `validateTask` (`evidence.service.ts:424`) and drained by `emitTaskValidated` (`:444–459`), reached from `TasksService` through the port contract (`backend/src/tasks/task-validation.port.ts:33–37`).
- `couponEvent` — returned out of the fulfilment transaction (`fulfilment.service.ts:751`) and emitted at `:767`.

**On rollback, nothing is emitted.** A throwing transaction propagates past the emit line, and the seed object is garbage-collected unread. The `P2002` replay path in `confirmPaidOrder` also deliberately does not re-emit (`fulfilment.service.ts:755–757`).

**Emission is synchronous.** `emitter.emit(...)` invokes listeners on the caller's stack in registration order. `emitAsync` is never used in production code — the only occurrence in the repo is a jest stub (`backend/src/test-utils/mock-providers.ts:143`). Two consequences worth stating: listeners declared `async` return a promise the emitter does not await, so the `try/catch` in `emitDomainEvent` catches only *synchronous* listener throws; and every async listener therefore carries its own `try/catch` (`notifications.listener.ts:17,29,43,55,72`; `staff-nudge.cron.ts:272`) or delegates to a never-rejecting call (`mission-bridge.listener.ts:14–17` documents `void this.bridge.apply(...)` as correct precisely because `apply` never rejects).

> ⚠️ **The whole eventing spine is best-effort, in-process and non-durable.** No broker, no outbox, no replay. A process restart between commit and emit loses the event with no recovery path. The system is built to tolerate this — the business writes are all inside the transaction and only notifications and realtime pushes ride on the events — but it should not be described as guaranteed delivery.

An `@upstash/qstash` `Receiver` is built in the constructor from both signing keys, and only if both are present (`:53–60`). The handler reads `upstash-signature` (`:72`), rejects a missing header with `UnauthorizedException('Missing QStash signature')` (`:85`), verifies at `:88`, and rejects a bad signature at `:89`.
- **Unconfigured behaviour, two independent paths.** *Publish side*: with no token or URL, `onModuleInit` warns "notifications will process inline (no queue)" and leaves the client null (`:20–25`); `publish()` then falls straight through to `processor.process(...)` inline, swallowing errors (`:53–60`). *Callback side*: a null receiver throws `ForbiddenException('QStash signing keys are not configured')` (`:79`) **unless** `QSTASH_ALLOW_UNSIGNED === 'true'` **and** `NODE_ENV !== 'production'` (`:76–77`) — so the unsigned path can never be reached in production, asserted at `notifications.controller.spec.ts:32`.
- **Retries and dedup:** `retries: 3` on the Upstash side (`:43`). **No deduplication is configured** — no `deduplicationId`, no `contentBasedDeduplication`, and no delay option anywhere. Duplicate suppression happens only downstream, in `NotificationDispatcher`'s cooldown keyed on `(user, type, reference_id)` (`notification-dispatcher.service.ts:70–81`).
- **Job vocabulary** (`notifications.processor.ts:17–42`): `notify-task-due`, `notify-task-blocked`, `notify-approval-pending`, `notify-low-stock`, `notify-new-order`, `notify-order-ready`, `notify-delivery-update`; unknown names log a warning (`:41`). Each handler is individually `try/catch`ed, so a webhook never 500s on a handler fault.

> ⚠️ **The signature is verified against a re-serialised body.** `notifications.controller.ts:88` calls `receiver.verify({ signature, body: JSON.stringify(body) })` **after** Nest's JSON parser has decoded the request — this is not the raw body, and no `rawBody` is preserved for this route (unlike `/webhooks/razorpay`, which does preserve it). Any key-order or whitespace difference between what QStash signed and what `JSON.stringify` reproduces will fail verification. It works today because both sides round-trip the same simple object shape; it is fragile rather than wrong.

> ⚠️ **`publish()` never rejects.** A publish failure is logged as "QStash publish failed, falling back to inline" and then runs the job inline (`:46–51`). This means a QStash outage never drops a notification — but it also means a job can run twice if QStash actually accepted the message before the client errored.

### 2.5 The `BridgeDispatch` exactly-once ledger

This is the **single durable exactly-once guarantee in the system**. Everything else — notifications, Pusher, the domain-event bus — is at-most-once and explicitly failure-isolated.

**The unique key** is `@@unique([rule_key, source_type, source_id])` — `backend/prisma/schema.prisma:865`. It deliberately excludes `node_id` and `event`, so the key is per-rule-per-subject, globally.

**The mechanism** is `MissionBridgeService.dispatchOnce` — `backend/src/mission-bridge/mission-bridge.service.ts:281–324`:

1. Open a transaction (`:289`) at **default isolation** — no level is passed. Deliberate: the unique index, not the isolation level, is the serialization point (`:273–275`).
2. **Claim first.** `tx.bridgeDispatch.create({ … outcome: applied })` at `:290–300` — the insert *is* the lock.
3. Run the rule body `fn(tx)` (`:301`).
4. Patch the claim with the decided outcome (`:302–310`).
5. On `P2002` (`hasPrismaCode` at `:314`, helper at `transaction-retry.ts:11`), log at debug and **`return null`** (`:315–318`).
6. On any other error, warn and **`return null`** (`:321–322`) — "the bridge must never fail the caller's request" (`:320`).

**States.** `BridgeOutcome` (`schema.prisma:26–32`): `applied` (`:27`, written at `mission-bridge.service.ts:297,:220,:425,:505`), `skipped_no_task` (`:213`), `skipped_no_mission` (`:437`), `skipped_no_owner` (`:450`), and `failed` — which **no code path ever writes**. A genuine failure rolls the claim back with the work, so no row survives to carry it. Because the claim is uncommitted until the whole transaction commits, a row is only ever *observed* in its terminal state.

**Retries.** There are none inside the bridge, by design (`:276–279`): a failure leaves no ledger row, so a later re-emit retries cleanly; only *decided* outcomes are recorded and are therefore permanent. The important corollary is that **a decided skip is permanent** — a `skipped_no_mission` row occupies the unique key forever, so once a mission exists a re-emit of the same event does nothing. That is deliberate and documented at `:408–411`: a rolled-back dispatch would silently retry forever, while a `skipped_no_mission` row says exactly why no task exists.

Twenty rules are declared in `mission-bridge.rules.ts`; seventeen carry `emitter: 'P3'` and are subscribed, five carry `emitter: 'P5'` and are filtered out of `P3_RULES` (`:399–401`). `feedback.received` maps to two rules (`:258,:272`), so one event writes two ledger rows under different `rule_key`s — which the unique key makes safe. A spec pins the subscribed set at sixteen events (`mission-bridge.service.spec.ts:917–923`). Observability is `GET /mission-bridge/dispatches`, gated on `MANAGE_SYSTEM` (`mission-bridge.controller.ts:15–16`).

### 2.6 The serializable-retry helper for money-path transactions

`backend/src/common/utils/transaction-retry.ts`, 44 lines, read in full:

- `SERIALIZABLE_TX_OPTIONS` (`:4–8`) — `{ isolationLevel: Serializable, maxWait: 5000, timeout: 15000 }`, documented at `:3` as "Options for every multi-write transaction in the money path."
- `hasPrismaCode(err, code)` (`:11–18`) — duck-typed so it works for real Prisma errors and test doubles alike.
- `withSerializableRetry<T>(fn, retries = 3, backoffMs = 25)` (`:25–44`). **Retries:** 3 *additional* attempts, so up to 4 total; no call site overrides the default. **Backoff:** `backoffMs * 2 ** (attempt - 1)` (`:39`) — 25 ms, 50 ms, 100 ms, no jitter. **Error code:** `P2034` and nothing else (`:35`); everything else, `P2002` included, is rethrown immediately. `P2034` is Prisma's wrapper for Postgres `40001` (serialization_failure) and `40P01` (deadlock_detected) — the raw SQLSTATEs are never matched anywhere in the repo.

**Twelve call sites, all of them money- or fulfilment-path:**

## 3. Critical flow traces

Four flows, each answered against the same twelve questions, each closing with a one-line verdict on whether the runtime tells the same story as the UX.

### 3a. KDS — Mark Ready

The reviewer's own worked example. A kitchen operator taps an item on the Kitchen Display; the item advances `preparing → ready`, stock is deducted, and when the last item lands the order flips.

**1. Who may invoke it.** `Permission.MANAGE_KITCHEN`, enforced by `@RequiresPermission(Permission.MANAGE_KITCHEN)` on both KDS routes — `backend/src/kitchen/kds/kds.controller.ts:25,31`. The gate itself is `PermissionsGuard.canActivate` (`backend/src/auth/permissions.guard.ts:15`), which resolves the caller's role permissions through `getPermissionsForRole` (`:38`) and additionally refuses any customer token outright (`:33`). Seeded holders of `MANAGE_KITCHEN`: `FOUNDER_ADMIN` and `TECH_LEAD` (both hold `Object.values(Permission)` — `backend/prisma/seed-data/roles.ts:19,130`), `BACKEND_LEAD` (`:63`) and `PROCUREMENT_LEAD` (`:96`). The same permission plus the `kds` module grant gates the realtime channel (`backend/src/realtime/realtime.channels.ts:12`).

**2. Which endpoint / command.** `PATCH /kitchen/kds/items/:id/status` with body `{ status }` — `backend/src/kitchen/kds/kds.controller.ts:30`. The id is `ParseUUIDPipe`-validated (`:33`) and the body is `@IsEnum(OrderItemStatus)`-validated (`:16`). The UI calls it from `frontend/components/ops/kitchen/kds/KdsBoard.tsx:56`, driven by a click on the item row (`frontend/components/ops/kitchen/kds/KdsOrderItem.tsx:38`) whose next status comes from a client-side map (`KdsOrderItem.tsx:13`).

**3. State transition.** Two guards, in order. First a whitelist: only `pending`, `preparing` and `ready` are acceptable at all, because the `OrderItemStatus` enum carries fulfilment members (`packed`/`shipped`/`delivered`/`attended`) the board must not set — `backend/src/kitchen/kds/kds.service.ts:127`, rejecting with `BadRequestException` at `:133`. Then a progression map **read inside the transaction**: `{ pending: 'preparing', preparing: 'ready' }` — `kds.service.ts:160`. The legal transition is `preparing → ready`; anything else throws `BadRequestException` naming the current status and the only valid next one (`:165`). A missing item throws `NotFoundException` (`:154`). Crucially the item is re-read inside the tx (`:150`) rather than trusted from a prior read, so the guard is evaluated against committed state.

**4. Transaction boundary and isolation level.** `this.prisma.$transaction(async (tx) => { … }, SERIALIZABLE_TX_OPTIONS)` wrapped in `withSerializableRetry` — `kds.service.ts:147`. `SERIALIZABLE_TX_OPTIONS` is `{ isolationLevel: Serializable, maxWait: 5000, timeout: 15000 }` (`backend/src/common/utils/transaction-retry.ts:4`). Inside the boundary: the item re-read, the progression guard, the full ingredient and prep-batch deduction, the item `status`/`ready_at` write, the not-ready sibling count, and the conditional order flip (`kds.service.ts:150–222`). Outside the boundary and strictly after commit: the domain event (`:239`) and the Pusher push (`:249`). Note the sibling `pending → preparing` branch uses the same Serializable options but is **not** retry-wrapped (`kds.service.ts:258,:290`) — see §2.6.

**5. Inventory deduction.** `FulfilmentService.deductItemIngredients(tx, item, actorForOrder(order), order.zone_id)` — called at `kds.service.ts:189`, implemented at `backend/src/fulfilment/fulfilment.service.ts:465`. Per `RecipeLine` of `input_type: 'ingredient'`: the per-serving quantity is multiplied by the item quantity (`:493,:498`), converted into the ingredient's base unit via `convertUnit` (`:505`, throwing if no conversion exists at `:511`), checked against `IngredientStock` for the item's zone (`:517`, throwing `Insufficient stock for …` at `:520`), decremented (`:526`), and paired with a `StockMovement` row of `movement_type: order_deducted`, negative quantity, `reference_type: 'order'`, `reference_id: order_id` and the resolved actor (`:531–546`). A product with no recipe — merchandise, experiences — has nothing to deduct (`:497`). The order must have a `zone_id` or the whole call is refused (`kds.service.ts:184`).

**6. Prep-batch deduction.** Same function, the `input_type: 'recipe'` branch — `fulfilment.service.ts:549`. The need is converted into the source recipe's yield unit (`:554`), then FIFO-drained across `active`, unexpired `PrepBatch` rows in the item's zone, ordered `expires_at asc, created_at asc` (`:566`). Each batch is decremented and flipped to `depleted` when it hits zero (`:580`). A shortfall after all batches throws `Insufficient prep batch stock for …` (`:592`), aborting the transaction. Note the KDS board only ever shows items whose recipe is `preparation_type: 'scratch'` (`kds.service.ts:69`) — every other preparation type was already deducted and set `ready` at order creation (`fulfilment.service.ts:381,405,412`), so this is the correct and only deduction point for scratch items.

**7. Order state effect.** After the item update, the service counts siblings that are not yet ready — `tx.orderItem.count({ order_id, id: { not: itemId }, status: { not: ready } })` at `kds.service.ts:209`. If that count is zero, the order is flipped to `OrderStatus.ready` in the same transaction (`:218`).

**8. Event emitted.** Two pushes, both after commit. `DomainEvent.ORDER_READY` is emitted only when the order actually flipped (`kds.service.ts:238`), carrying `orderId`, `channel`, `createdBy` and the standard `domainEventBase(node_id, actor)` prefix (`:240`). Its one consumer is `NotificationsListener.handleOrderReady` (`backend/src/notifications/notifications.listener.ts:25`), which publishes `notify-order-ready` to QStash inside its own try/catch (`:28`). Separately, and on **every** status change including `pending → preparing`, `RealtimeService.emit('private-kds', 'kds.order.updated', { item_id, status })` fires (`kds.service.ts:249,292`). The payload deliberately carries no board state so it can never be stale — the board refetches on receipt (`:248`; client side `KdsBoard.tsx:24,62`). `RealtimeService.emit` swallows its own failures so a dropped push degrades to the 30-second poll (`backend/src/realtime/realtime.service.ts:57`).

**9. Duplicate-click and replay protection.** **There is no client-side in-flight guard.** `KdsOrderItem` renders a `role="button"` div with an unconditional `onClick` (`frontend/components/ops/kitchen/kds/KdsOrderItem.tsx:38`); neither it nor `KdsBoard` passes `statusMutation.isPending` down to disable it (`KdsBoard.tsx:54–87`). A double-tap therefore fires two `PATCH` requests. The **server** is what makes this safe, in two layers: (a) if the first request has committed, the second re-reads the item inside its own transaction, finds `status: 'ready'`, and `progressionMap['ready']` is `undefined`, so the guard throws `BadRequestException` (`kds.service.ts:165`) — no second deduction; (b) if the two requests are genuinely concurrent and both read `preparing`, Serializable isolation aborts one with Prisma `P2034`, `withSerializableRetry` re-runs it up to 3 times with 25 ms exponential backoff (`backend/src/common/utils/transaction-retry.ts:25,35`), and the retry then hits case (a). Either way stock is deducted exactly once. There is no idempotency key and none is needed — the status guard *is* the idempotency mechanism.

**10. Rollback behaviour.** Everything that matters is inside one transaction, so any throw — insufficient stock (`fulfilment.service.ts:520`), missing unit conversion (`:511`), prep-batch shortfall (`:592`), illegal transition (`kds.service.ts:165`), missing zone (`:184`) — rolls back the item status, every `IngredientStock` decrement, every `StockMovement` row, every `PrepBatch` decrement and the order flip together. Because the domain event and the Pusher push are emitted only from the resolved value **outside** the transaction (`:235`), a rollback can never leak an `order.ready` for an order that did not become ready.

**11. Audit actor recorded.** ⚠️ **No `AuditEvent` is written by this flow.** `KdsService`'s constructor takes `PrismaService`, `FulfilmentService`, `EventEmitter2` and `RealtimeService` — `kds.service.ts:52`; `AuditService` is not injected. The only actor trail is on the `StockMovement` rows, which carry `actor_type`, `actor_id` and `created_by` from `actorForOrder(order)` (`fulfilment.service.ts:542`). `actorForOrder` resolves in priority order `created_by` (user) → `customer_id` (customer) → system with a null id (`fulfilment.service.ts:320–329`). Because `updateItemStatus` is never threaded the authenticated user's id (`kds.service.ts:122` takes only `itemId` and `newStatus`), **the operator who tapped the button is not recorded anywhere.** For a POS-created order the movement is attributed to whoever created the order; for a marketplace order, to the customer. This is the single largest audit gap in the four flows.

**12. Readiness-XP consequences.** N/A because readiness meters and XP are driven exclusively by the task-validation cascade (`backend/src/evidence/evidence.service.ts:406,409`); nothing in the KDS path touches `Task`, `TaskReadinessEvent`, `ReadinessMeter` or `User.xp_total`.

**Two further observations the reviewer will want.**

> ⚠️ **The KDS writes `Order.status` directly, bypassing the order state machine.** `STATUS_TRANSITIONS` (`backend/src/orders/orders.service.ts:56`) declares `placed → [confirmed, preparing]` and `preparing → [ready]`, and is enforced on the manual route at `orders.service.ts:368`. But `getActiveOrders` shows orders in `placed` *or* `preparing` (`kds.service.ts:62`), and the flip at `kds.service.ts:218` is an unguarded `tx.order.update` — so an order still in `placed` can jump straight to `ready`, a transition the manual endpoint would reject. `ShipmentsService.propagateToOrder` does the same thing in the other direction, writing `OrderStatus.shipped` directly (`backend/src/shipments/shipments.service.ts:676`). This is defensible design — the KDS and the courier are the authorities on their own legs — but it means `STATUS_TRANSITIONS` gates only the manual `PATCH /orders/:id/status` route and is not a system-wide invariant. It should not be described as one.

> ⚠️ **A mixed-fulfilment order never flips to `ready`.** The sibling count at `kds.service.ts:209` treats every status other than `ready` as outstanding, and shipped lines are set to `OrderItemStatus.packed` at confirmation (`fulfilment.service.ts:1058`). A marketplace order carrying one scratch kitchen line and one shipped line will therefore keep at least one non-`ready` sibling forever, so the last kitchen item marks ready without flipping the order and without emitting `order.ready`. In practice the shipment lifecycle later drives that order to `shipped` (`shipments.service.ts:676`), so nothing is stuck — but the "when the last item lands, the order flips" story only holds for single-fulfilment orders. Unverified whether this is intentional; no comment in either file addresses it.

**Waste %.** N/A to this flow — marking an item ready writes no `WasteLog` row. The `Waste: N%` figure on the KDS top bar (`frontend/components/ops/kitchen/kds/KdsMetricsBar.tsx:54`) is a derived read from `GET /kitchen/metrics`, computed as today's `WasteLog.cost_impact` sum divided by the pro-rated recipe cost of today's prep batches (`backend/src/kitchen/metrics/kitchen-metrics.service.ts:96–111`). Waste rows come from the waste module and from `KitchenExpiryCron` (`kitchen-expiry.cron.ts:59`), never from Mark Ready.

> **Verdict — KDS: Mark Ready.** Runtime and UX agree on the substance: the deduction, the sibling count, the order flip and the Pusher refresh all do exactly what the board implies, and the Serializable transaction plus the in-transaction status guard make a double-tap safe without any client-side lock. Two mismatches: **the operator is not recorded anywhere** (no `AuditEvent`, and `StockMovement` is attributed to the order's creator, not the person who tapped), and **a double-tap surfaces as a red "Failed to update status. Try again." toast** (`KdsBoard.tsx:65`) rather than a silent no-op, because the server correctly answers the second click with a 400 the client renders as failure.

### 3b. Checkout — `payment.captured` → `confirmPaidOrder`

The single "paid marketplace order" write. Everything commercial about a paid order commits together; a crash after the commit can lose events but never money (`backend/src/fulfilment/fulfilment.service.ts:608–623`).

**1. Who may invoke it.** Two entry points, neither of them permission-gated in the staff sense. (a) The storefront confirm endpoint: `POST /customer/orders/confirm`, gated by `CustomerGuard` on the whole controller with `@Public()` to bypass the global JWT guard — `backend/src/customer-orders/customer-orders.controller.ts:27–29,79`. Authorisation is ownership: the pending payload's `customer_id` must equal the authenticated customer or the request is refused with `ForbiddenException` (`backend/src/customer-orders/customer-orders.service.ts:595`). (b) The Razorpay webhook: `POST /webhooks/razorpay`, `@Public()`, `@HttpCode(200)`, throttled to 100/min — `backend/src/webhooks/webhooks.controller.ts:26–29`. Its authorisation is an HMAC over the preserved raw body, verified **before any other processing** (`backend/src/webhooks/webhooks.service.ts:49–55`), plus mandatory `x-razorpay-signature` and `x-razorpay-event-id` headers (`webhooks.controller.ts:35,37`).

**2. Which endpoint / command.** `FulfilmentService.confirmPaidOrder(input)` — `fulfilment.service.ts:624`. Called from `customer-orders.service.ts:641` with `placedVia: OrderSource.storefront`, and from `webhooks.service.ts:207` with `placedVia: OrderSource.webhook_fallback`. The webhook path is reached only for `payment.captured` / `order.paid` events whose `notes.type === 'marketplace'` (`webhooks.service.ts:78,97`).

**3. State transition.** The order is **created**, not transitioned: `status: OrderStatus.placed` with a nested `Payment` at `PaymentStatus.paid` (`fulfilment.service.ts:657,675`). Per-line routing then moves items: `shipped` lines to `packed` (`:1058`), `booking` lines to `ready` with their `EventBooking` promoted to `confirmed`/`paid` (`:1146,:1206`), and `local` lines through `applyPrepTypeOnCreate` (`:690`) which sets every non-scratch line `ready` (`:412`) and leaves scratch lines `pending` for the KDS. The illegal path is the seat that cannot be taken: `BookingSeatUnavailableError` (`:1139`) aborts the whole transaction and diverts to refuse-and-refund (`:774`) — **never a partial confirmation** (`:1115`).

Two guards run before the money path is entered on the storefront route: the Razorpay payment signature (`customer-orders.service.ts:600`, rejecting at `:605`), and a belt-and-braces re-fetch of the payment from Razorpay's API requiring `captured` or `authorized` (`:610–617`) and an exact paise-for-paise amount match (`:621`).

**4. Transaction boundary and isolation level.** `withSerializableRetry(() => this.prisma.$transaction(async (tx) => { … }, SERIALIZABLE_TX_OPTIONS))` — `fulfilment.service.ts:633`, closing at `:752`. Serializable, `maxWait: 5000`, `timeout: 15000`, retried up to 3 times on `P2034` with 25 ms doubling backoff (`transaction-retry.ts:4,25`). Inside the boundary, all of: zone resolution (`:635`), the `Order` + `OrderItem[]` + `Payment` nested create (`:637`), the fulfilment re-read (`:688`), prep-type routing and stock deduction (`:690`), shipped-line packing (`:1058`), booking-hold confirmation or re-acquisition (`:1064`), coupon redemption (`:1075`), loyalty spend (`:1088`), the optional `order.booking_reacquired` audit row (`:709`), the `order.confirmed` audit row (`:728`), and the final read-back (`:747`). Outside, after commit: `order.confirmed` (`:758`) and `coupon.redeemed` (`:767`).

The numbers are deliberately **not** recomputed inside the transaction — `pending` is the quote the customer was shown and paid against, and recomputing would let a catalog edit between quote and confirm change what was charged (`:620–622`).

**5. Inventory deduction.** Via `applyPrepTypeOnCreate` (`:690`), restricted to lines with `fulfilment === FulfilmentType.local` (`:693`). Per line: `ready_to_sell`/`assemble` recipes go through the same `deductItemIngredients` BOM path as the KDS (`:410`), `batch_prepared` goes through `deductBatchPrepared` (`:408`), and `scratch` is skipped entirely (`:405`) because the KDS deducts it at Mark Ready. Every non-scratch line is then set `ready` with a `ready_at` (`:412`). Actor is the customer (`:694`).

**6. Prep-batch deduction.** Two routes. `deductBatchPrepared(tx, recipeId, quantity, zoneId)` (`:420`) FIFO-drains `active`, unexpired batches in the zone ordered `expires_at asc, created_at asc` (`:426`), decrements each, flips exhausted ones to `depleted` (`:441`), and throws `Insufficient prepared batch quantity for recipe …` on shortfall (`:454`). Additionally, any `recipe`-type `RecipeLine` reached through `deductItemIngredients` FIFO-drains prep batches the same way (`:566`).

**7. Order state effect.** The `Order` row is created at `placed` (`:657`) with `placed_via` recording which surface produced it (`:658`), `created_by: null` (`:659`) and the marketplace `zone_id` (`:660`). Money columns are copied verbatim from the frozen quote; `discount_amount` folds coupon and loyalty together because `Order` carries one discount column (`:628–630,:645`); `tax_amount` is carved *out of* subtotal and never added to total (`:647`); `loyalty_points_earned` is `0` because points are credited on delivery, not on payment (`:652`).

**8. Event emitted.** `DomainEvent.ORDER_CONFIRMED` after commit, carrying `orderId`, `orderNumber`, `channel`, `total`, `itemCount`, `customerId` (`fulfilment.service.ts:758`), consumed by `MissionBridgeListener` (`backend/src/mission-bridge/mission-bridge.listener.ts:58`). Then `coupon.redeemed`, held back from inside the transaction and emitted here so the SPEC §4.1 after-commit rule holds (`:767`; the reason is stated at `:1040`) — though as §2.1 records, that event currently has **no consumer**, its bridge rule being P5-gated (`mission-bridge.rules.ts:372–382,:399`). The P2002 replay path deliberately **does not** re-emit — the order was confirmed once (`:756`). Both callers additionally push `order.placed` on the customer's own Pusher channel `private-customer-{id}`, after the transaction, with the failure logged and swallowed (`customer-orders.service.ts:673`; `webhooks.service.ts:233`).

**9. Duplicate-click and replay protection.** Four independent layers.
- **Webhook dedup:** `webhook_processed:{eventId}` set in Redis with `SET NX EX 86400`; a second delivery of the same event id returns `{ status: 'duplicate' }` without processing (`webhooks.service.ts:65–67`). This **fails closed** — with Redis down the webhook is rejected with a 503 so Razorpay retries later (`:59–64`).
- **Pending-key consumption:** the storefront path peeks the pending order non-consumingly first so a rejected signature does not burn the session (`customer-orders.service.ts:578`), then consumes it with an atomic `GETDEL` so exactly one caller proceeds (`:626`). A loser resolves to the existing order or gets a 409 (`:627–636`).
- **The unique payment id — the real replay guard.** `Payment.razorpay_payment_id` is `@unique` (`backend/prisma/schema.prisma:1547`). A replayed capture trips Prisma `P2002`, which is caught outside the transaction and resolved to the already-created order via `findOrderByRazorpayPaymentId` (`fulfilment.service.ts:777–782`, lookup at `:601`). The client is told the same thing: "A replay of the same payload returns the *same* order, not an error, so a retried confirm is always safe" (`frontend/components/storefront/checkout/PayButton.tsx:124`).
- **Client-side:** one idempotency key per quote, held in a ref and regenerated only when the quote id changes (`PayButton.tsx:99–105`; the key lands on `Order.idempotency_key`, itself `@unique` at `schema.prisma:1480`), the last payment payload retained so a failed confirm can be retried without re-paying (`:107`), and the pay button disabled for the whole `creating | open | confirming` window (`:264,:282`).

**10. Rollback behaviour.** The transaction has already rolled back by the time either catch branch runs, so nothing partial exists — stated at `fulfilment.service.ts:771`. Three outcomes:
- `BookingSeatUnavailableError` → **refuse and refund** (`:774`, implemented `:812`). Three writes in a fixed order: a `cancelled` `Order` with `cancelled` items and a `paid` `Payment`, deliberately **unzoned** so it never reaches a kitchen queue (`:896–945`), plus an `order.payment_refused` audit row (`:947`); then the gateway refund through `RefundsService` as the system actor (`:836`); then `OrderRefusedAndRefundedException` telling both callers the payment is *resolved* so the pending key must not be restored. A gateway that refuses the refund is **not** allowed to undo step 1 — the `Refund` row stays `failed`, an `order.auto_refund_failed` audit row is written (`:848`), and the exception still reports `refunded: false` (`:865`). The reasoning is recorded at `:787–810`: losing the order row would leave a captured payment with nothing attached, the exact defect being fixed.
- `P2002` → resolve to the existing order (`:777`).
- Anything else → rethrow, and the caller restores the pending session key with `SET … NX` so a retry or the webhook fallback can still create the order (`customer-orders.service.ts:665`; webhook equivalent `webhooks.service.ts:225`).

**11. Audit actor recorded.** Yes, inside the transaction. `order.confirmed` with `...AuditService.customer(customerId)` and an `after` block carrying status, `placed_via`, `razorpay_payment_id`, total, discount, shipping, tax, coupon code and points redeemed (`fulfilment.service.ts:728–745`). Conditionally, `order.booking_reacquired` listing every re-seated line (`:709`) — a fact invisible on the order row that has to be recoverable when someone asks why an event went over its old count (`:705–707`). On the refusal path, `order.payment_refused` and possibly `order.auto_refund_failed`, both as `ActorType.system` with a null actor id (`:952,:854`). `AuditService.customer` is defined at `backend/src/audit/audit.service.ts:57`.

**12. Readiness-XP consequences.** N/A because nothing in the checkout path writes `Task`, `TaskReadinessEvent`, `ReadinessMeter` or `User.xp_total`. The only cross-domain consequence is `order.confirmed` reaching `MissionBridgeListener` (`mission-bridge.listener.ts:58`), which materialises mission work rather than moving a meter.

**The hold re-seat branch, in detail.** The 15-minute booking hold and the 30-minute pending-order key have different lifetimes, so a customer who pays late has their seat swept by `EventHoldsCron` through no fault of their own (`fulfilment.service.ts:1107–1111`). Before the fix, `applyCommercialEffects` simply threw and left a captured payment with no order at all. Now `planBookingSeats` (`:1241`) decides each line read-only: a **surviving hold** is promoted to `confirmed` with `hold_expires_at` cleared and `razorpay_payment_id` nulled — that id belongs to the order's `Payment` row and copying it would make a second booking on the same payment impossible (`:1146–1154`, reasoning at `:1118`). A **swept hold** is re-acquired inside the same Serializable transaction using the same `capacity − confirmed − live holds` arithmetic the quote used (`:1113`), reusing the existing row where one exists because at most one booking can exist per `(event, customer_phone)` (`:1156–1172`). Capacity is deliberately **not** re-checked for a surviving hold — that seat was never given back, and re-checking would let a staff member who shrank an event turn a legitimately held seat into a refund (`:1232–1235`). Only a line that genuinely cannot be re-seated raises `BookingSeatUnavailableError`, and then for the whole order.

> **Verdict — Checkout.** Runtime and UX agree, and this is the most carefully built path in the system. The single Serializable transaction, the unique-payment-id replay guard, the refuse-and-refund branch and the after-commit event discipline all match what the storefront tells the customer ("you will not be charged twice", "tap retry"). No mismatch found. The one thing worth stating explicitly: the storefront's belt-and-braces re-fetch and amount check (`customer-orders.service.ts:610–623`) run on the confirm path but **not** on the webhook fallback, which relies on the HMAC plus a paise comparison against the stored pending payload (`webhooks.service.ts:196–203`) — a deliberate and adequate difference, not a defect, but an asymmetry a reviewer should know about.

### 3c. Daily Close — Sign

Signing a business day freezes its metrics for good. Two gates, both required.

**1. Who may invoke it.** Two independent checks. **Gate one** is `@RequiresPermission(Permission.MANAGE_OPS)` on the route (`backend/src/daily-close/daily-close.controller.ts:58`), enforced by `PermissionsGuard` (`backend/src/auth/permissions.guard.ts:15`). Seeded `MANAGE_OPS` holders: `FOUNDER_ADMIN`, `TECH_LEAD`, `FRONTEND_LEAD` (`backend/prisma/seed-data/roles.ts:39`), `PROCUREMENT_LEAD` (`:100`) and `DESIGN_OUTREACH_LEAD` (`:147`). **Gate two** is membership of `SystemSetting['daily_close'].signer_role_codes`, checked in the service after a fresh `User → role.code` read (`backend/src/daily-close/daily-close.service.ts:279–287`), throwing `ForbiddenException` naming the roles that may sign (`:284`). Seeded value: `['FRONTEND_LEAD', 'FOUNDER_ADMIN']` (`backend/src/settings/settings.service.ts:109`). The distinction is deliberate and documented: "may run operations" and "is accountable for the day" are different claims, and SPEC names the second (`daily-close.controller.ts:17`, `daily-close.service.ts:265`). The intersection of both gates is therefore `FOUNDER_ADMIN` and `FRONTEND_LEAD` — which is why `FRONTEND_LEAD` carries an otherwise-surprising `MANAGE_OPS` grant, with the reason written into the seed (`roles.ts:35–38`).

**2. Which endpoint / command.** `POST /daily-close/:date/sign` with an optional `{ notes }` body — `daily-close.controller.ts:57`. `:date` is a node-local `YYYY-MM-DD` rejected with a 400 by `assertBusinessDateKey` before any query runs (`:68`, contract at `:20`). The actor id comes from `req.user.id` (`:64`). The UI is `frontend/components/ops/daily-close/DailyCloseSignCard.tsx:145`.

**3. State transition.** `open → signed`, once. The row is re-read inside the transaction (`daily-close.service.ts:290`); a missing row throws `NotFoundException` (`:299`), and a row already `signed` throws **`ConflictException('This day is already signed')` → HTTP 409** (`:301`). The update writes `status`, `signed_by`, `signed_at` and `notes` together (`:305–313`). There is no path back: nothing in the service ever writes `status` away from `signed`.

**4. Transaction boundary and isolation level.** `this.prisma.$transaction(async (tx) => { … })` at `daily-close.service.ts:289` — **default isolation (Read Committed), not Serializable, and no retry wrapper.** Inside: the re-read, the 409 guard, the status update and the audit row. Outside and before: the settings read (`:276`), the node read (`:277`) and the signer-role check (`:279`) — so a `signer_role_codes` change landing between the check and the commit would not be seen, a negligible window for a hand-edited setting.

**5. Inventory deduction.** N/A because signing writes no stock. `DailyClose.metrics` already contains the day's figures, computed earlier by `computeAndUpsert` (`:243`) from read-only aggregates over `Order`, `Refund`, `WasteLog`, `AuditEvent` and `Shipment` (`:412,439,448,467,479`).

**6. Prep-batch deduction.** N/A — same reason.

**7. Order state effect.** None. Signing does not touch `Order`; it freezes a computed summary of orders already in their final states.

**8. Event emitted.** ⚠️ **None.** No `emitDomainEvent` call, no `eventEmitter` injection in `DailyCloseService` (constructor at `:226–230`: `PrismaService`, `AuditService`, `SettingsService`, `NodeService`), and no Pusher push. The sign-off is recorded as an `AuditEvent` and nothing subscribes to it. Downstream consumers — notably the morning brief, which reads yesterday's `DailyClose.metrics` at 07:00 (`backend/src/ai/morning-brief/morning-brief.service.ts:174`) — poll the row rather than react to an event. This is a defensible design for a once-a-day artefact, but it means "the day was signed" has no push consumer.

**9. Duplicate-click and replay protection.** Both halves present, and this flow is the contrast case to the KDS. Server-side, the second sign gets a **409** from the in-transaction status guard (`daily-close.service.ts:301`) — refused, not idempotent-by-overwrite, which is the right answer for a signature. Client-side, the submit button and the confirm control are both `disabled={signMutation.isPending}` (`DailyCloseSignCard.tsx:309,333,339`), and a 409 is handled explicitly with `toast.info('Someone else signed this day — refreshing.')` plus a refetch (`:160–163`), while a 403 renders the server's own message naming who may sign (`:166–169`). The already-signed state renders as "a receipt, not a form" (`:179–180`). The 409 behaviour is recorded as verified at runtime — `.planning/phases/35-p6-run-it-layer/35-01-SUMMARY.md:125`.

**10. Rollback behaviour.** The status update and the audit row share one transaction (`:289`), so a failed audit write rolls the signature back with it — the day cannot become signed without its audit row, or vice versa. There is no compensating action and none is needed: nothing outside the transaction is mutated.

**11. Audit actor recorded.** Yes, and this is load-bearing: RUN-02 says the sign-off *is* an `AuditEvent`. Written inside the same transaction (`:318`) with `entity_type: DAILY_CLOSE_ENTITY_TYPE` (`:66`), `action: DAILY_CLOSE_SIGNED_ACTION` (`:69`), `...AuditService.user(userId)` (`:323`, helper at `backend/src/audit/audit.service.ts:50`), `before: { status }` and an `after` block carrying status, business date, notes **and the frozen metrics** — so the audit row stays self-contained even if the `DailyClose` row is later archived (`:315–331`).

**12. Readiness-XP consequences.** N/A because signing writes no `Task`, `TaskReadinessEvent`, `ReadinessMeter` or `User.xp_total`. Readiness appears only as a *read* inside `metrics`.

**The frozen row.** Freezing is enforced at the recompute path, not the sign path: `computeAndUpsert` returns the existing row untouched when `existing.status === signed` (`:252`), so a `POST /:date/recompute` on a signed day is a satisfied no-op rather than an error — the request succeeded, the artefact is frozen, and the caller can see both from the response (`daily-close.controller.ts:43–48`). The nightly cron takes the same path (`daily-close.cron.ts:70`), so a signed day is never silently recomputed. The UI mirrors the rule in words: "A signed close is frozen and cannot be recomputed" (`DailyCloseSignCard.tsx:322`).

> **Verdict — Daily Close: Sign.** Runtime and UX agree completely, and this is the best-behaved flow of the four on duplicate protection: a real 409 from an in-transaction guard, a disabled button, and a client that handles the conflict as information rather than failure. Two things worth noting rather than calling mismatches: the transaction runs at **default isolation with no retry**, unlike the money paths (justified — a single-row status flip guarded by a re-read has no serialization anomaly to defend against); and the frontend keeps its **own hardcoded copy of the signer roles** at `frontend/lib/types/daily-close.ts:39`, which the file itself documents as a display-only convenience that can drift, costing "a confusing button, never an unauthorised signature" (`:34–37`).

### 3d. Task status → validation cascade

The flow the reviewer should scrutinise hardest, because it is the one that was found broken and repaired: a task whose evidence was approved *before* it was marked done never became `valid`, never awarded XP and never moved its readiness meter (`backend/src/tasks/tasks.service.ts:506–512`).

**1. Who may invoke it.** Resolved in the service, not by a route decorator — `PATCH /tasks/:id` carries no `@RequiresPermission` (`backend/src/tasks/tasks.controller.ts:101`), so `PermissionsGuard` lets any authenticated staff member through (`permissions.guard.ts:36`) and the real check is `TasksService.update`: `UPDATE_ANY_TASK`, **or** `UPDATE_OWN_TASK` *and* `existing.owner_user_id === requestingUser.id` (`tasks.service.ts:357–366`), otherwise `ForbiddenException`. Permissions are loaded in parallel with the task (`:348`). Seeded holders: `UPDATE_OWN_TASK` is granted to every role (`backend/prisma/seed-data/roles.ts:30,55,75,90,112,141`); `UPDATE_ANY_TASK` only to `FOUNDER_ADMIN` and `TECH_LEAD` via `Object.values(Permission)` (`:19,:130`). The kanban mirrors this exactly — a card is draggable only when `task.is_own === true || isAdmin` (`frontend/components/ops/tasks/TaskKanban.tsx:163`).

**2. Which endpoint / command.** `PATCH /tasks/:id` (`tasks.controller.ts:101`), UUID-validated, dispatching to `TasksService.update(id, dto, { id, roleCode })` (`:108`). The UI reaches it by dragging a card between kanban columns (`TaskKanban.tsx:206`) or from the task sheet.

**3. State transition.** Free-form on `Task.status` — there is no from→to whitelist for tasks, unlike orders. Two hard guards instead: (a) a task with an unfinished `depends_on_task_id` cannot be set `done`, rejected with `BadRequestException` naming the blocking task (`tasks.service.ts:376–386`); (b) `subject_type` and `subject_id` must move together or not at all (`:369`). `completed_at` is set when moving to `done` and cleared when leaving it (`:431–435`). Two transitions are removed from the UI rather than the API: `blocked` and `cancelled` are unreachable by drag because blocking needs a reason and cancelling needs intent — both have their own dedicated paths (`TaskKanban.tsx:202–204`). A drop onto the task's current column returns early (`:200`).

**4. Transaction boundary and isolation level.** `this.prisma.$transaction(async (tx) => { … }, { isolationLevel: Prisma.TransactionIsolationLevel.Serializable })` — `tasks.service.ts:403`, options at `:525`. Serializable but **not** wrapped in `withSerializableRetry`, so a `P2034` serialization abort surfaces to the caller as a 500 rather than being retried; the money paths take the retry, this one does not. Inside the boundary: the field-by-field update (`:437`), approval re-materialisation or clearing (`:447–488`), quest and mission progress recalculation (`:492`), the `task.status_changed` audit row (`:497`), and the whole validation cascade (`:520`). Outside, after commit: `task.validated` (`:531`).

**5. Inventory deduction.** N/A because tasks never touch stock.

**6. Prep-batch deduction.** N/A — same reason.

**7. Order state effect.** N/A because tasks and orders are disjoint domains; nothing in `TasksService.update` reads or writes `Order`.

**8. Event emitted.** `DomainEvent.TASK_VALIDATED`, after commit, and **only on the `false → true` transition** — the emit is a no-op when the seed is null (`tasks.service.ts:531`; `EvidenceService.emitTaskValidated` at `backend/src/evidence/evidence.service.ts:444–459`, guarding at `:448`). The seed is produced inside the transaction and carried out (`:424–435`) precisely so the after-commit emit and the response body can both see what validation decided (`tasks.service.ts:405`). `emitDomainEvent` swallows listener failures (`backend/src/common/events/domain-events.ts:302–312`), so a broken listener cannot fail the task update. The sibling `block` path emits `TASK_BLOCKED` the same way (`tasks.service.ts:609`), consumed by `NotificationsListener` (`backend/src/notifications/notifications.listener.ts:63`).

> ⚠️ **`task.validated` has no consumer.** There is no `@OnEvent(DomainEvent.TASK_VALIDATED)` anywhere in the codebase and no `BridgeRule` for it (§2.1). It is emitted from four call sites — `evidence.service.ts:507,:553`, `approvals.service.ts:619` and `tasks.service.ts:531` — and lands nowhere. Nothing is broken by this: every consequence of validation (XP, quest and mission progress, the readiness meter) is written *inside* the transaction by `validateTask`, not by a listener. But the event is currently a hook with nothing on it, and "when a task validates, the system notifies X" is not a claim the runtime supports.

**9. Duplicate-click and replay protection.** Client-side, a repeat drop onto the same column short-circuits before any request (`TaskKanban.tsx:200`). Server-side there is **no idempotency key and no status guard** — a repeated `PATCH {status: 'done'}` is accepted and simply rewrites the same values. That is safe by construction rather than by check: `validateTask` is idempotent. It recomputes `valid` from first principles (`evidence.service.ts:386`), computes `newlyValid = isValid && task.valid !== true` (`:391`) so the event fires once, recalculates XP by **aggregating** valid tasks rather than incrementing (`:216–219`), and creates a `TaskReadinessEvent` only if no un-revoked one exists (`:262–279`). A second identical PATCH therefore writes the same row values, awards no second XP and creates no second readiness event — but it *does* write a second `task.status_changed` audit row, because `statusChanged` compares the incoming dto against the pre-update row (`tasks.service.ts:388`) and a repeat with the same status makes that false. So the duplicate audit row only appears on an actual status change, and a true double-click writes one row.

**10. Rollback behaviour.** Everything — the task update, the approval rows, the progress recalculations, the audit row, `valid`/`valid_xp`/`verified`, `User.xp_total`/`level`, the `TaskReadinessEvent` and the `ReadinessMeter` update — is inside the one Serializable transaction (`:403–526`), so any throw unwinds the lot. Because the event is emitted from the carried-out seed rather than from inside, a rollback cannot leak a `task.validated` for a task that did not validate.

**11. Audit actor recorded.** Yes, twice over, both in-transaction. `task.status_changed` with `...AuditService.user(requestingUser.id)`, `before: { status }`, `after: { status }` (`tasks.service.ts:497–504`). And on the approval-gate edits: `task.approvals_cleared` when `requires_approval` goes true→false (`:457–464`). `ApprovalPolicyService.backfillMissing` writes `task.approvals_backfilled` on its own path (`backend/src/approvals/approval-policy.service.ts:246`).

**12. Readiness-XP consequences.** This is the substance of the cascade, and it runs **on every status change, not just `→ done`** (`tasks.service.ts:514–519`) — because validity is `done + approved evidence + approvals satisfied`, so `done → todo` has to take the XP and the meter contribution back off again. The chain, in `EvidenceService.validateTask` (`evidence.service.ts:340`):

1. **Validity** = `status === done` **and** at least one `approved` evidence row (counted with a filtered `_count`, `:361–365,:373`) **and**, when `requires_approval`, `ApprovalPolicyService.isSatisfied` (`:377`).
2. **`isSatisfied`** (`approval-policy.service.ts:203`) reads every `Approval` for the entity; **zero rows returns `false`** (`:215`) — under v1 "no rows" counted as satisfied, so the approval gate never actually ran (`evidence.service.ts:334–338`). Any `rejected` row returns `false` (`:221`). Otherwise the resolved policy decides: `n_of` needs `approved >= min_approvals`, anything else needs unanimity (`:224–226`).
3. **Write-back:** `valid`, `valid_xp` and `verified` on the task (`:396–403`). `valid_xp` is the task's XP scaled by type — `core` 100 %, `improvement` 80 %, `adhoc` 70 % (`:200–208`).
4. **XP:** `recalculateUserXp` **aggregates** `valid_xp` across the owner's valid tasks and rewrites `xp_total` and `level` (`:215–235`). Level thresholds 200 / 500 / 1000 (`:224–229`). Because it aggregates rather than increments, it is naturally idempotent and self-correcting.
5. **Quest and mission progress** recomputed (`:407–408`) — this is the authoritative pass, which is why the pre-validation recompute in `TasksService.update` is left in place as the earlier one (`tasks.service.ts:517`).
6. **Readiness:** `applyReadinessFromTask` (`:243`) creates a `TaskReadinessEvent` when valid and none is active (`:262–279`), or revokes all active ones with `revoked_at`/`applied: false` when not (`:282–292`). It then **always** recomputes the task-driven half by summing un-revoked events, capped at 100 (`:296–304`), and publishes `ReadinessMeter.current_value` through the single shared `blendMeterValue` rule so the task-driven half and the formula half can never write the published value by two different rules (`:315–326`).

**The port.** `TasksService` reaches `EvidenceService` through `TASK_VALIDATION_PORT`, a DI symbol (`backend/src/tasks/task-validation.port.ts:41`) bound lazily via `ModuleRef` in `tasks.module.ts:43`. The reason is a genuine two-level dependency cycle: `EvidenceModule` imports `TasksModule` and `EvidenceService` injects `TasksService`, so a direct constructor dependency would close both at once, and a one-sided `forwardRef` would boot on one import order and throw on another (`task-validation.port.ts:10–28`). The two imports in that file are type-only and must stay that way. There are now five call sites for `validateTask`: `TasksService.update` (`tasks.service.ts:520`), evidence approve and reject (`evidence.service.ts:504,548`), approvals approve and reject (`backend/src/approvals/approvals.service.ts:528,542`), plus the backfill (`approval-policy.service.ts:386`).

> **Verdict — Task status → validation cascade.** Runtime and UX agree, and the cascade does exactly what the readiness ring implies: XP and meter movement follow validity, and validity follows `done + approved evidence + satisfied approvals` in both directions. The design is idempotent by construction — aggregate-not-increment XP, existence-checked readiness events, `newly_valid` gating the event — rather than by an idempotency key, which is the stronger property. Two things to state plainly: the Serializable transaction here is **not** retry-wrapped, so a serialization abort under concurrent edits surfaces as a 500 rather than a retry; and `PATCH /tasks/:id` carries no route-level permission decorator, so the authorization story lives entirely in the service (`tasks.service.ts:357`) — correct, but invisible to anyone auditing the controllers alone.
