# Phase 23 — UI Design Contract

> Visual and interaction contract for Phase 23: Razorpay Payments + Customer Auth.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value | Source |
|----------|-------|--------|
| Tool | shadcn | `components.json` detected |
| Style | base-nova | `components.json` → `"style": "base-nova"` |
| Base color | neutral | `components.json` → `"baseColor": "neutral"` |
| CSS variables | true | `components.json` → `"cssVariables": true` |
| Component library | base-ui (shadcn base-nova uses base-ui primitives) | `components.json` |
| Icon library | lucide | `components.json` → `"iconLibrary": "lucide"` |
| Font | Plus Jakarta Sans | `globals.css` → `--font-plus-jakarta` |
| Theming model | `--public-*` CSS vars for all customer-facing surfaces | `globals.css` — warm/light always-on palette |

### Theming Rule (CRITICAL)

All customer-facing screens (OTP login, event checkout, customer profile) MUST use the `--public-*` token set, not the ops `--primary`/`--background` tokens. The public layout already enforces `class="light"` — customer screens are always light mode. POS Razorpay addition (staff-facing) uses the standard ops `--primary` token set.

## Spacing Scale

Declared values (multiples of 4 only):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, OTP digit gaps |
| sm | 8px | Compact element spacing, label-to-input gap |
| md | 16px | Default element spacing, form field gaps |
| lg | 24px | Section padding, card internal padding |
| xl | 32px | Layout gaps, between major form sections |
| 2xl | 48px | Major section breaks, page vertical padding |
| 3xl | 64px | Page-level spacing (unused in compact mobile flows) |

Exceptions:
- OTP digit input boxes: `min-width: 44px; min-height: 44px` (WCAG touch target, existing pattern from `EventBookingForm` stepper buttons)
- Payment status icon containers: `48px` centered vertically (visual prominence for success/failure states)

## Typography

All sizes use `font-sans` (Plus Jakarta Sans) already applied globally via `globals.css`.

| Role | Size | Weight | Line Height | Usage |
|------|------|--------|-------------|-------|
| Body | 14px (`text-sm`) | 400 (`font-normal`) | 1.5 | Form labels, helper text, muted descriptions — use `text-[var(--public-muted)]` color to distinguish from body-prominent; do NOT use a separate weight for this distinction |
| Body prominent | 16px (`text-base`) | 400 (`font-normal`) | 1.5 | Input values, card body text, OTP instructions — use `text-[var(--public-fg)]` |
| Heading | 20px (`text-xl`) | 600 (`font-semibold`) | 1.2 | Section headings ("Verify your phone", "Book Your Spot") |
| Display | 24px (`text-2xl`) | 600 (`font-semibold`) | 1.1 | Page-level heading ("Welcome back" pattern from staff login) — size alone (24px vs 20px) provides hierarchy; do NOT use font-bold (700) |

Declared weights: **400 and 600 only**. font-bold (700) is not used in this phase.

Notes established from existing pattern:
- `text-[var(--public-fg)]` for heading/body text on customer surfaces
- `text-[var(--public-muted)]` for secondary/helper text (replaces a separate 14px weight distinction — muted color is sufficient)
- `font-mono tabular-nums` for monetary amounts (₹ prefix, established in POS)

## Surface Layout Contract

### Surface 1: Customer OTP Login Flow

**Route:** `/login` or modal overlay on event booking page (to be decided by planner, but UI contract is the same)

The OTP flow has three sequential sub-screens rendered in the same panel. The panel dimensions match the existing staff auth layout right-panel: `max-w-sm mx-auto` centered, full height flex.

**Sub-screen 1: Phone Entry**
- Layout: Single input + CTA button, `space-y-8` wrapper (matches staff login)
- Heading: "Enter your phone" at display size (24px semibold)
- Subheading: "We'll send a 6-digit OTP via WhatsApp" at body size (14px muted)
- Input: `type="tel"` with `+91` prefix label inline, `h-10 rounded-lg border border-[var(--public-border)] bg-white` (matches staff login input pattern)
- CTA: Full-width `h-11 rounded-lg bg-[var(--public-terracotta)] text-white` button labeled "Send OTP"
- Loading state: Loader2 spinner + "Sending..." label inside button (matches staff login)

**Sub-screen 2: OTP Entry**
- Layout: 6-cell OTP input row + verify button + resend link
- OTP cells: 6 individual `input[maxlength=1]` boxes, `size-11` (44px), centered, `gap-2`, numeric keyboard on mobile (`inputMode="numeric"`)
- Auto-advance: focus moves to next cell on digit entry; backspace focuses previous cell
- Verify CTA: Full-width `h-11 bg-[var(--public-terracotta)]` button labeled "Verify Code"
- Resend link: below button, `text-sm text-[var(--public-muted)]` with terracotta resend text, disabled with countdown `(59s)` after first send
- Rate limit warning: amber info banner `border border-amber-200 bg-amber-50 text-amber-700` when 3rd OTP request attempted

**Sub-screen 3: Name Capture (first-time customers only)**
- Triggered if `customer.name` is null after OTP verification
- Layout: Single optional name input + skip link + save button
- Heading: "What should we call you?" at heading size
- Subheading: "Optional — helps us personalise your experience"
- Input: standard phone-entry input style
- CTA: "Save name" (primary) | "Skip for now" (text link, `text-[var(--public-muted)]`)

**Interaction states (all sub-screens):**
- Error: `rounded-lg border border-red-200 bg-red-50 px-4 py-3 text-sm text-red-700` — matches staff login error pattern
- Disabled inputs during submission: `disabled:opacity-50` (matches staff login)
- Already-verified banner: `border border-[var(--success)]/20 bg-[var(--success)]/10 text-[var(--success)]` (matches EventBookingForm success pattern)

### Surface 2: Event Booking Checkout (Replaces EventBookingForm)

**Route:** `/events/[id]` — replaces `EventBookingForm` component

The existing `EventBookingForm` is replaced by `EventCheckoutForm`. When customer is not logged in, show OTP login inline (collapsed panel expands). When logged in, show the booking form.

**Not-logged-in state:**
- Replace form with a prompt card: `rounded-xl border border-[var(--public-border)] bg-[var(--public-surface)] p-6`
- Icon: `Smartphone` lucide icon, `size-8 text-[var(--public-muted)]`
- Heading: "Log in to book" (20px semibold)
- Body: "We'll send an OTP to your WhatsApp number" (14px muted)
- CTA: "Log in with WhatsApp" — terracotta button, full-width `h-11`
- Clicking expands OTP sub-screen inline (no page navigation)

**Logged-in state (customer verified):**
- Display customer identity strip: `bg-[var(--public-surface)] rounded-lg px-4 py-2 flex items-center gap-3`
  - Phone verified badge: `CheckCircle2` lucide icon, `size-4 text-[var(--success)]`
  - Phone number: `text-sm font-medium text-[var(--public-fg)]`
  - "Not you?" link: `text-xs text-[var(--public-muted)] hover:text-[var(--public-terracotta)]`
- Guest count stepper: keeps existing pattern (`Minus`/`Plus` icon buttons, `min-h-[44px] min-w-[44px]`)
- Optional name input: pre-filled from `customer.name` if set, otherwise empty (editable)

**Free event path (price = 0):**
- CTA: "Reserve My Spot" — same terracotta button
- No Razorpay modal opens; direct booking confirmation

**Paid event path (price > 0):**
- CTA: "Book & Pay ₹{total}" — terracotta button showing calculated amount
- Pressing CTA → backend creates Razorpay order → opens Razorpay modal
- See Razorpay Modal Integration section below

**Payment states visible on our UI (outside the Razorpay modal):**

| State | Visual |
|-------|--------|
| idle | Normal CTA button |
| creating-order | Button disabled + Loader2 spinner + "Preparing payment..." |
| razorpay-open | Button disabled + "Payment in progress..." (modal is open) |
| payment-success | Success panel (CheckCircle2 icon, green, "You're booked!" message) |
| payment-failed | Error banner + "Try again" button re-enabled |
| capacity-exceeded-post-payment | Red error banner + auto-refund notice "Your payment has been refunded" |
| session-expired | Info banner "Your session timed out — restart booking" + refresh CTA |

## Razorpay Modal Integration Contract

The Razorpay checkout.js modal is a **third-party UI element**. The document below specifies exactly what we control vs what Razorpay controls.

### Script Loading

```
<script src="https://checkout.razorpay.com/v1/checkout.js" />
```

Load dynamically in a `useRazorpay` hook (not in `<head>` — only load when needed). Check `window.Razorpay` before instantiation.

### What We Control (via options object)

| Property | Value | Purpose |
|----------|-------|---------|
| `key` | `process.env.NEXT_PUBLIC_RAZORPAY_KEY_ID` | Authentication (public key, safe to expose) |
| `order_id` | From backend `/payments/create-order` | Links modal to our order |
| `amount` | NOT sent from frontend | Set by backend when creating order |
| `currency` | `"INR"` | Currency |
| `name` | `"Konma Xperience"` | Merchant name shown in modal header |
| `description` | Contextual: `"Event Booking: {event.title}"` or `"Order #{order_number}"` | Sub-header in modal |
| `image` | `/logo.png` full URL | Merchant logo in modal (square, 256x256 recommended) |
| `prefill.name` | Customer name (if set) | Pre-fills name field in modal |
| `prefill.contact` | Customer phone (`+91` prefixed) | Pre-fills phone in modal |
| `prefill.email` | Customer email (if set) | Pre-fills email in modal |
| `notes` | `{ type: 'event_booking', entity_id: '<uuid>' }` | Webhook routing metadata (per D-23) |
| `theme.color` | `#c2410c` (terracotta — `--public-terracotta`) | CTA button + active tab color in Razorpay modal |
| `theme.backdrop_color` | `rgba(28, 25, 23, 0.7)` | Overlay backdrop color (warm dark) |
| `modal.backdropclose` | `false` | Prevent accidental dismissal |
| `modal.escape` | `true` | Allow Escape key to dismiss |
| `modal.confirm_close` | `true` | Show "are you sure?" when closing during payment |
| `modal.animation` | `true` | Keep modal animation |
| `modal.ondismiss` | callback → sets state to `payment-failed` or `modal-dismissed` | Handle close |
| `handler` | callback → receives `{razorpay_payment_id, razorpay_order_id, razorpay_signature}` | Payment success (pre-verification) |
| `retry` | `{ enabled: true, max_count: 3 }` | Allow retry within same modal |

### What Razorpay Controls (we do NOT style or override)

| Element | Razorpay owns |
|---------|---------------|
| Payment method tabs | UPI, Cards, Netbanking, Wallets — tabs and icons |
| Card number/expiry/CVV input form | Razorpay's PCI-compliant UI |
| UPI ID input + intent deeplink | Razorpay's UI |
| Wallet selection grid | Razorpay's UI |
| EMI calculator / offers display | Razorpay's UI |
| Payment processing animation | Razorpay's loading spinners |
| Success/failure screens within modal | Razorpay's UI |
| Modal container frame, padding, border radius | Razorpay's UI |
| Mobile bottom sheet vs desktop popup | Razorpay's responsive behavior |
| Branding footer ("Secured by Razorpay") | Cannot be removed |

### Integration Pattern Summary

Our app is responsible for:
1. "Pay" button state machine (idle → creating-order → modal-open → success/failure)
2. Calling `POST /payments/create-order` to get `razorpay_order_id`
3. Opening modal via `new Razorpay(options).open()`
4. Handling `handler` callback: POST to `POST /events/:id/bookings/confirm` or `POST /payments/razorpay/confirm` with signature
5. Handling `ondismiss`: reset button state, show retry if applicable
6. Showing our own success UI after confirmed booking (outside Razorpay modal)

Razorpay modal lifecycle from our perspective:
```
[Our button] → creating-order (API call)
  → razorpay-open (modal.open())
    → [User interacts inside Razorpay modal — we see nothing]
    → EITHER: handler(response) called → payment-success → our confirm API call
           OR: modal.ondismiss called → payment-failed or modal-dismissed
```

## Interaction States Reference

### State Machine: OTP Login

```
idle
  → sending [Send OTP pressed]
    → otp-sent [API returns 200]
    → rate-limited [API returns 429]
  → verifying [Verify Code pressed]
    → verified [API returns 200 + token set]
    → wrong-code [API returns 401 — wrong OTP]
    → expired-code [API returns 410 — OTP TTL exceeded]
    → rate-limited [API returns 429]
  → name-capture [if customer.name is null post-verify]
    → complete [name saved or skipped]
```

### State Machine: Event Booking

```
idle
  → creating-order [Book & Pay pressed]
    → razorpay-open [order created, modal.open() called]
      → payment-success [handler() called]
        → confirming [POST confirm API called]
          → booked [booking created]
          → capacity-exceeded [race condition — auto-refund triggered]
      → modal-dismissed [ondismiss without payment]
    → create-order-failed [API error]
  → booking-free [Reserve My Spot pressed, price = 0]
    → booked [direct API call, no Razorpay]
```

## Accessibility Contract

- All OTP inputs: `aria-label="Digit {n} of 6"`, `inputMode="numeric"`, `pattern="[0-9]*"`
- Phone input: `autoComplete="tel"`, `inputMode="tel"`
- Customer Profile "Edit name" pencil icon button: `aria-label="Edit name"`
- Payment state announcements: `role="status"` on payment progress container (live region)
- Success state: `role="status"` on success panel (polite announcement)

- Minimum touch targets: 44px × 44px for all interactive elements (matches existing `min-h-[44px] min-w-[44px]` in EventBookingForm)
- Razorpay modal: Razorpay's responsibility for modal accessibility
