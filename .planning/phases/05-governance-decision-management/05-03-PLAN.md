NOTE: The `approvalId` here uses `evidence.id`. However, the backend override endpoint expects an Approval record ID, not an Evidence ID. Since the current approval queue fetches evidence (not approval records), the override endpoint in Plan 01 should accept evidence ID and internally find the associated approval, OR the ApprovalItem should have access to the approval ID. For Phase 5, simplify: the backend override endpoint POST `/approvals/:id/override` should accept the evidence ID and find the pending approval for that evidence entity. Update the understanding: the `approvalId` prop maps to `evidence.id`, and the backend will look up the Approval record where `entity_type='evidence' AND entity_id=evidence.id AND status='pending'`.

Alternative (cleaner): Change the approvalId to be a generic identifier. The OverrideDialog calls `POST /evidence/${evidence.id}/override` and the backend adds an override endpoint on the EvidenceReviewController. This aligns better with the existing pattern. The Plan 01 executor should decide — document this flexibility in the action.

PRACTICAL approach: Use `POST /approvals/${evidence.id}/override` where the ID is the EVIDENCE id. The backend ApprovalsService.overrideApproval should find the approval record by `entity_id: evidenceId, entity_type: 'evidence', status: 'pending'` instead of finding by approval primary key. This avoids needing to change the frontend data model.
