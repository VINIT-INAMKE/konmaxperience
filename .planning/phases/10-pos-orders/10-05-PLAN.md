    1. **DeliveryQueueTable** — `frontend/components/ops/pos/DeliveryQueueTable.tsx`:
      - Props: `orders: Order[]`, `isLoading: boolean`, `onDeliveryUpdate: () => void`
      - Uses shadcn Table with columns:
        a. **Order #**: `#{order.id.slice(-4).toUpperCase()}` in Geist Mono 14px/700
        b. **Customer**: customer_name or customer_phone or "—"
        c. **Address**: delivery_address (truncate with title tooltip if long, max 40 chars display)
        d. **Assigned To**: If delivery_assigned_to exists, show name text. If not, show "Assign" button that opens Popover.
        e. **Delivery Status**: Show current status with DELIVERY_STATUS_LABELS badge. If null, show "Awaiting pickup" in muted text.
        f. **Actions**: Single button for NEXT delivery status transition:
          - If delivery_status is null or undefined: "Mark Picked Up" button
          - If delivery_status is 'picked_up': "Mark In Transit" button
          - If delivery_status is 'in_transit': "Mark Delivered" button
          - If delivery_status is 'delivered': no button (this order should not be in the queue anyway)
          Per UI-SPEC: only the NEXT status button shown — reduces cognitive load.

      - **Assign Popover** — For rows without delivery_assigned_to:
        - Popover trigger: "Assign" button (outline variant, small size)
        - Popover content: Input (placeholder "Rider or staff name" per UI-SPEC), "Save" button
        - On save: `useMutation({ mutationFn: (name) => apiClient.patch('/orders/' + order.id + '/delivery', { delivery_assigned_to: name }) })`. On success: close Popover, call onDeliveryUpdate (refetches). Optimistic update: show name immediately.

      - **Status advance mutation**: `useMutation({ mutationFn: ({ orderId, status }) => apiClient.patch('/orders/' + orderId + '/delivery', { delivery_status: status }) })`. On success: call onDeliveryUpdate (refetches). On error: Sonner toast "Could not update order status. Refresh and try again." per UI-SPEC. Optimistic update: show new status immediately.

      - Empty state: "No active deliveries" heading + "Delivery orders in progress will appear here." body per UI-SPEC copywriting contract.

    2. **Delivery queue page** — `frontend/app/(ops)/pos/delivery/page.tsx`:
      - Query: `useQuery(['orders', 'delivery-queue'], () => apiClient.get('/orders?channel=delivery'))`. Filter on the frontend for active only: `orders.filter(o => o.status !== 'cancelled' && o.delivery_status !== 'delivered')`. This is acceptable because delivery orders are a small subset.
      - Alternative: Add backend filter by passing `status=placed,preparing,ready,dispatched` — but the backend getOrders supports single status filter, not multi. For simplicity, filter client-side on the small delivery subset.
      - Refetch on delivery update callback.
      - Page header: "Delivery Queue" heading. Below: DeliveryQueueTable.
      - Auto-refresh: `refetchInterval: 15000` (15 seconds) to pick up new delivery orders without manual refresh.
