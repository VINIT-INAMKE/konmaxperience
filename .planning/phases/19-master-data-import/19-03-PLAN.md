POST /imports/parse (multipart/form-data):
- Body: file (File), importType (string: 'ingredients' | 'vendors' | 'vendor_pricing')
- Response: ParseResult
```typescript
interface ParseResult {
  importType: ImportType;
  rows: ImportRow[];
  totalRows: number;
  validCount: number;
  invalidCount: number;
  duplicateCount: number;
  columns: string[];
}
interface ImportRow {
  rowIndex: number;
  raw: Record<string, string>;
  validated: Record<string, unknown>;
  errors: CellError[];
  status: 'valid' | 'invalid' | 'duplicate';
  existingId?: string;
}
interface CellError { field: string; message: string; }
```

- Body: { importType: string, rows: ImportRow[], updateExisting?: boolean }

```typescript
interface CommitResult {
  imported: number;
  updated: number;
  skipped: number;
  errors: number;
  errorDetails: Array<{ rowIndex: number; message: string }>;
}
```

Create `frontend/app/(ops)/admin/import/[type]/page.tsx` — the full import flow page.

This is a `'use client'` component implementing the complete import workflow per CONTEXT.md D-01 through D-19 and UI-SPEC interaction contracts.

**Page Structure (per UI-SPEC layout):**
```
[Back link → /admin/import] [Page header: "Import {TypeLabel}" + description]
[Download Template section — two buttons: XLSX and CSV]
[Upload Zone — drag-drop or file picker]
[Parse File button — appears after file accepted]
[Update existing records toggle — appears after parse]
[Row count summary — "X rows parsed, Y valid, Z invalid"]
[Preview Table — appears after parse, with sticky header]
[Import N Records button — disabled when no valid rows]
[Import result summary — appears after commit]
```

**Key implementation details:**

1. **Route params and validation:**
   - Read `type` from `useParams()` (Next.js dynamic route)
   - Validate against `IMPORT_TYPES` array — redirect to /admin/import if invalid
   - Load config from `IMPORT_TYPE_CONFIG[type]`

2. **State management (useState hooks):**
   - `file: File | null` — selected file
   - `isDragOver: boolean` — drag hover state
   - `parseResult: ParseResult | null` — parsed rows from backend
   - `isParsing: boolean` — parse loading state
   - `rows: ImportRow[]` — mutable copy of parseResult.rows (for inline editing)
   - `editingCell: { rowIdx: number; field: string } | null` — currently editing cell
   - `editValue: string` — current edit input value
   - `updateExisting: boolean` — upsert toggle (default false) per D-17
   - `commitResult: CommitResult | null` — result after commit
   - `isCommitting: boolean` — commit loading state

3. **Download Template section (per D-07, D-11):**
   - Two buttons side by side: "Download Template (.xlsx)" and "Download Template (.csv)"
   - XLSX: `window.open(apiBaseUrl + '/imports/template/' + type, '_blank')` or use `apiClient` to fetch blob
   - CSV: `window.open(apiBaseUrl + '/imports/template/' + type + '/csv', '_blank')`
   - Use FileDown icon from lucide-react on buttons
   - Button variant="outline"

4. **Drag-drop Upload Zone (per D-01, UI-SPEC interaction contracts):**
   - Custom div with `onDragOver`, `onDragLeave`, `onDrop` handlers
   - Default state: dashed border using `border-dashed border-2 border-[var(--border)]`, Upload icon (lucide, size 48px), "Drag and drop your CSV or XLSX file here" primary label, "or click to browse" secondary label in muted
   - Drag-over state: `border-[var(--primary)] bg-[var(--muted)]` per UI-SPEC
   - Hidden `<input type="file" accept=".csv,.xlsx" />` triggered by clicking the zone
   - Accepted MIME types: `text/csv`, `.csv`, `.xlsx`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`
   - File accepted state: zone collapses to compact chip showing filename + size + X remove button (per UI-SPEC)
   - Validate file type on drop/select — show error for unsupported types: "Only CSV and XLSX files are accepted" per UI-SPEC copywriting

5. **Parse File button:**
   - Appears only when file is accepted and parseResult is null
   - On click: create FormData with `file` and `importType`, POST to `/imports/parse`
   - Use `fetch` with credentials: 'include' for multipart (not apiClient.post which uses JSON)
   - During parse: show Skeleton rows in table area
   - On success: set parseResult and rows (deep copy for editing)
   - On error: show toast with "Could not read this file. Make sure it is a valid CSV or XLSX and try again."

6. **Preview Table (per D-02, D-14, D-15, UI-SPEC interaction contracts):**
   - Uses shadcn `Table`, `TableHeader`, `TableRow`, `TableCell`, `TableHead`
   - First column: "Status" with colored dot Badge (green variant for valid, destructive for invalid, amber/warning for duplicate) per D-15
   - Subsequent columns: one per column in `parseResult.columns`
   - Invalid cells: red border-bottom `border-b-2 border-[var(--destructive)]` + Tooltip on hover showing error message per D-14
   - Duplicate rows: Badge shows "Duplicate — will skip" when toggle is OFF, "Duplicate — will update" when toggle is ON per UI-SPEC copywriting
   - Wrapper: `overflow-x-auto` for horizontal scroll, sticky header via `sticky top-0 z-10 bg-[var(--background)]`
   - Row count summary above table: "{totalRows} rows parsed, {validCount} valid, {invalidCount} invalid" + "{duplicateCount} duplicates" if any

7. **Inline Cell Editing (per D-03, D-16, UI-SPEC):**
   - Click any cell in a row to activate inline editing
   - Replace cell text with shadcn `Input` size="sm" pre-filled with current value
   - Press Enter or click away (onBlur) to commit edit
   - On commit: update the `raw` field in the local `rows` state for that row/field
   - After edit: re-parse that single row by calling `POST /imports/parse` with a single-row CSV (or locally re-validate if feasible)
   - Simpler approach: update `raw[field]` in state, mark row for re-validation, and provide a "Re-validate" button that re-sends the entire dataset to the parse endpoint
   - Simplest viable approach (recommended): On cell edit commit, update `rows[idx].raw[field]` in local state, then locally clear the error for that field from `rows[idx].errors`. The actual server-side re-validation happens at commit time. If the cell was the only error, change status to 'valid'. This avoids re-calling parse.

8. **"Update existing records" toggle (per D-17, UI-SPEC):**
   - Appears below the upload zone, above or alongside the table
   - shadcn `Switch` + label "Update existing records"
   - Helper text below: "Matching by name — existing records will be overwritten"
   - Default OFF (skip duplicates)
   - Toggle changes local state `updateExisting`, affects duplicate row badge text

9. **Import N Records button (per D-04, UI-SPEC):**
   - Count valid rows: `rows.filter(r => r.status === 'valid' || (r.status === 'duplicate' && updateExisting)).length`
   - Label: "Import {N} Records"
   - Disabled when N = 0, or isParsing, or isCommitting
   - Loading state: Loader2 spinner + "Importing..."
   - On click: POST `/imports/commit` with JSON body `{ importType: type, rows, updateExisting }`
   - Use `apiClient.post<CommitResult>('/imports/commit', { importType: type, rows, updateExisting })`
   - On success: set commitResult, show toast "{N} records imported successfully" per UI-SPEC
   - On error: show error toast "Import failed. Try again or contact support."

10. **Import Result Summary (per D-19, UI-SPEC):**
    - Four stat blocks in a horizontal grid (grid-cols-2 md:grid-cols-4)
    - Each block: large number (text-2xl font-bold) + label below (text-xs text-muted-foreground)
    - "Imported" in green (text-green-600), "Updated" in blue (text-blue-600), "Skipped" in muted, "Errors" in red (text-red-600)
    - If errors > 0: amber Alert below with message: "{X} rows had errors and were not imported. Fix them inline and re-import."
    - After successful commit: Import button becomes disabled
